# OrbitFabric v1.4.0 — Core Interface and Public Adapter Onboarding

Release date: **2026-09-25**  
Status: **Published Core product release**  
GitHub Release: [OrbitFabric v1.4.0](https://github.com/OrbitFabric/orbitfabric/releases/tag/v1.4.0)

## Summary

OrbitFabric Core 1.4.0 adds a supported, no-clone public adapter onboarding path and further candidate Core-owned declarations and evidence contracts. The release builds on the v1.3.0 Adapter Management foundation without changing the stable Mission Data Contract's semantic authority or promoting candidate interfaces into stable commitments.

The Core package version is `1.4.0`. Contract maturity and independent wire-version identifiers must be evaluated **per surface**, not inferred from the product version.

## Added capabilities

### Public adapter installation and product distribution

The Core CLI now composes exact-version Catalog selection and a separately distributed GitHub Release Source:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r https://github.com/OrbitFabric/orbitfabric/releases/download/v1.4.0/orbitfabric-install.txt
orbitfabric adapter install fprime --version 0.1.3
orbitfabric adapter list
```

The published installation manifest identifies the exact Core 1.4.0 and GitHub Release Source 0.1.0 wheels using SHA-256 URL fragments. Installation from these released wheels requires no Git checkout. This is a GitHub Release-based distribution path; **no PyPI publication is implied**.

The Catalog can be loaded from the canonical GitHub repository at a resolved commit, from an explicit `--catalog-revision`, or from a local `--catalog` snapshot. Exact identity and version selection fail closed on missing or ambiguous matches. The provider-specific Release Source resolves and verifies release material outside Core; Core continues to own installation, installed state, acceptance and verification through the Adapter Manager.

This is **not** a provider-neutral discovery or dispatch framework. There are no version ranges, automatic upgrades, `latest` resolution, or provider selection policy. The previous explicit local-descriptor installation path and Project Lock workflows remain available.

See [Public Adapter Onboarding](../reference/public-adapter-onboarding.md), [Adapter Manager M0](../reference/adapter-manager-m0.md) and [Adapter Catalog CLI](../reference/adapter-catalog-cli.md).

### Core Interface Manifest (candidate)

```bash
orbitfabric export core-interface --json core_interface.json
```

The mission-independent `orbitfabric.core_interface` `0.1-candidate` declaration lists Core-owned structured capabilities with independent contract kind/version identities. Its deterministic RFC 8785/JCS SHA-256 fingerprint covers the interface declaration, **not** the executable version or environment. Consumers check required capability IDs and contract kinds/versions, rather than treating the product version as a compatibility handshake.

See [Core Interface Manifest](../reference/core-interface-manifest.md).

### Scenario Declaration Surface (candidate)

```bash
orbitfabric export scenario-declaration examples/demo-3u/scenarios/battery_low_during_payload.yaml --json scenario_declaration.json
```

The `orbitfabric.scenario_declaration` `0.1-candidate` export provides a deterministic, Core-normalized inventory of authored Scenario atoms with exact consumed-source SHA-256 provenance and structured failure behavior. It describes **declared** Scenario meaning, not host-side execution or native observations.

See [Scenario Declaration Surface](../reference/scenario-declaration-surface.md).

### Scenario Projection Accounting (candidate generic contract)

The `orbitfabric.scenario_projection_accounting` `0.1-candidate` Result-owned artifact records explicit adapter-declared dispositions for exact Scenario atoms. Core publishes schema, fixtures and generic conformance checks; an adapter owns the projection dispositions and mapping associations. Missing accounting is not inferred as failure, success or unsupported projection.

See [Scenario Projection Accounting Contract](../reference/scenario-projection-accounting-contract.md).

### Evidence Set Manifest (candidate generic contract)

The `orbitfabric.evidence_set_manifest` `0.1-candidate` contract provides typed correlation and byte-integrity references for retained evidence. Core owns the generic schema and checks. Evidence curators own inclusion/correlation and producers retain authority over the contents and native meaning of evidence.

See [Evidence Set Manifest Contract](../reference/evidence-set-manifest-contract.md).

## Compatibility and boundary

**Preserved stable boundaries:**

- Documented Mission Model semantics and the Mission Data Contract established at v1.0.0
- v1.2.0 stable Mission Snapshot and coherent Core Integration Input Set
- Existing stable diagnostic, report and admitted relationship-family compatibility commitments

**New or retained candidate boundaries:**

- Core Interface Manifest and Scenario Declaration Surface
- Scenario Projection Accounting and Evidence Set Manifest contracts
- Core inspection surfaces introduced in v1.1.0
- Projection Profile, Integration Result, Integration Package / operation-input lanes
- Adapter Release Descriptor, Project Lock, Catalog and Adapter Manager lifecycle

A `0.1-candidate` wire identifier is not evidence that a surface is unstable when a separate stable-classification decision has been made, and a `1.4.0` package release does not automatically stabilize a candidate contract. Those distinctions are documented in the [Stability and Compatibility Contract](../reference/stability-compatibility-contract.md).

Core remains the semantic authority for the Mission Model, not a flight software framework, a ground segment, a spacecraft simulator or a target-specific adapter runtime. Native systems own their implementations and runtime observations.
